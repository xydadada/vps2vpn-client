## 范围、证据和架构

基线树包含 1438 个文件和两个固定 Git 子模块。代码生成结果、二进制、资产和仅枚举的文件不能算成人工逐行审查。各专项覆盖台账明确区分全文阅读、局部调用链追踪、自动检查、生成代码及尚未全文阅读；仍在补查的文件不能写成“已全部审完”。最终总覆盖清单汇合这些证据，避免重复计数。

应用通过 Flutter/Riverpod 管理配置、持久化和界面；桌面 Core 经 Rust IPC 与受控子进程运行，Android 则经 Kotlin ServiceState/gomobile 调用 Go。Go 包装层调用固定 mihomo 子模块。配置还会经过数据库、Profile/Script 暂存文件、用户覆盖和增强策略，必须同时检查“当前运行配置”和“之后重新启动读取的配置”。服务端的订阅、会员 API、证书 pin、流量反馈是另一条跨仓库数据链。

审查采用固定源码、完整调用链和失败路径分析，并用真实 CI 验证。开始阶段的本地执行环境随后失联，最终代码通过 GitHub MCP 从固定基线重建、创建 blob/tree/commit 和更新审计分支；失联前的测试不能证明现在的提交。所有生成代码与依赖锁变更取自真实工具执行输出，不手工猜测哈希和校验和。

## 关键设计与兼容性

### 跨仓库 TLS 信任

服务端默认自签名面板不能靠关闭全局证书校验获得安全兼容。客户端从已保存的 HY2/TUIC 节点读取同面板主机的 SHA-256 叶证书 pin，并要求实际连接的host和port一致；固定 pin 的连接使用独立SecurityContext。无pin时正常验证PKI；非同主机节点的证书不能借用。HTTP订阅来源只改变会员API为HTTPS，保留有效端口，包括HTTP默认80，不能直接丢掉端口改成443。

仅REALITY、自签名面板又无对应pin时会明确失败。初始订阅若经不可信HTTP传输，内容和pin本身也不可信；这条引导信任问题没有被本PR假装解决。服务端原JSON字段和token路径保持兼容；新增TLS指纹字段是客户端内部可选元数据。

### 异步文件发布

下载完成不意味着旧请求仍有发布权限。Profile与Script分别维护每ID的操作令牌、当前记录/URL与owner存活检查；编辑、删除和新操作撤销旧令牌。文件在同文件系统的独立暂存位置完成写入后，最后一次检查和rename位于同一Dart事件轮次，避免检查后await再次让出控制权。没有预删旧文件。Setup缺失文件下载、普通更新、本地编辑保存均经过相同约束。

这种办法保护一个运行进程中的请求顺序，不能让文件和SQLite自动变成跨进程或断电事务。恢复全局状态与进程崩溃恢复仍是单独的设计问题。

### Android与桌面生命周期

Android关闭UI可能只需解绑仍在运行的VPN，不能把桌面的停止语义硬套过去。新发起但尚未确认的启动若被更新意图撤销，需要有序停止它；原本已在后台运行的VPN则应保留。Dart生命周期队列与Kotlin服务意图代数共同处理这个区别，失败清理必须保留可重试的租约/状态。

上游controller修复保持子模块gitlink不变，通过固定输入、输出和补丁blob校验、锁和幂等工具应用；Desktop构建hook和Android构建都执行同一检查。升级上游时必须重新审查，不能无条件对陌生版本打补丁。

## 尚需单独验证的边界

- Android真机VPN/TUN、权限对话框、Wi-Fi/蜂窝/无网络的真实交接；Windows真实系统代理与启动项、macOS权限/系统交互；编译和假服务测试不能代替它们。
- 公网丢包、MTU/PMTUD、双栈故障、跨国链路和受限网络下的吞吐/延迟，需要受控设备与真实网络。本轮未编造性能增幅或协议排名。
- 当前代码与固定第三方源码的selected-call-path审阅不等于第三方整个项目的逐行审计；依赖扫描也只覆盖数据库已知条目。
- 用户导入的配置、脚本及MITM模块的信任决定仍由用户和产品的权限模型承担；有界解析/传输不会把不可信脚本变成可信脚本。
